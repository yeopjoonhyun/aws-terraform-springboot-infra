# 프로젝트 회고

## 1단계 개발 환경

11월 7~8일에 공개 저장소를 만들고 macOS에 Terraform, AWS CLI, GitHub CLI를 설치했다. Terraform으로 인프라 구성을 코드에 남기고, AWS CLI로 실제 생성 결과를 확인할 수 있게 환경을 구성했다. 공개 저장소에는 코드와 설정 예시를 올리고, Terraform이 리소스 상태를 기록하는 `*.tfstate`와 개인 설정값이 담긴 `*.tfvars`, `.env`는 `.gitignore`에 등록했다. [개발 환경 설정](01-dev-environment.md), [Git 제외 설정](../.gitignore)

첫 푸시는 GitHub의 비공개 이메일 보호 기능에 걸려 `GH007`로 거부됐다. 이 저장소의 커밋 이메일을 GitHub가 제공한 noreply 주소로 바꾼 뒤 첫 커밋을 올렸다. 공개 저장소에서 검토할 정보에는 파일 내용뿐 아니라 커밋 작성자 정보도 포함된다는 것을 배웠다. [첫 푸시 기록](devlog.md#2026-11-07-2)

## 2단계 AWS 네트워크

### VPC 생성이 막힌 이유를 찾은 과정

VPC 코드의 `terraform validate`와 `plan`은 통과했지만 서울 리전에서 `apply`를 실행했을 때 조직의 서비스 제어 정책(SCP)이 `ec2:CreateVpc`를 명시적으로 거부했다. 같은 자격 증명으로 `aws sts get-caller-identity`는 성공했고 서울에서 VPC를 조회하는 요청도 SCP로 거부됐다. 처음에는 무료 플랜 제한으로 추정해 유료 플랜으로 올렸지만 서울의 거부는 이어졌다. [초기 실패 기록](devlog.md#트러블슈팅-apply-실패-scp-explicit-deny)

같은 계정으로 `describe-vpcs`의 리전만 바꿔 비교했다. 시드니에서 조회가 성공했고 서울·도쿄·미국 동부에서는 같은 거부가 돌아왔다. 기본 리전을 시드니로 바꾸고 VPC를 생성한 뒤 AWS CLI로 확인하고 삭제했다. 다시 한다면 플랜을 바꾸기 전에 오류에 나온 AWS 작업과 리전을 기록하고, 같은 조회를 다른 허용 후보 리전에서도 실행해 범위를 좁힐 것이다. [리전 변경과 검증](devlog.md#해결-scp는-플랜이-아니라-리전-제한이었다)

### 네트워크 구성과 검증

VPC의 두 가용 영역에 퍼블릭, 프라이빗 앱, 프라이빗 DB 서브넷을 한 개씩 두어 총 6개를 만들었다. 서브넷은 Terraform 맵에 정의하고 `for_each`로 생성했다. AWS CLI로 인터넷 게이트웨이를 향하는 기본 경로가 퍼블릭 라우팅 테이블에 있고, 그 테이블을 퍼블릭 서브넷 2개가 사용한다는 것을 확인했다. [네트워크 설계](02-network-design.md), [서브넷 Terraform 코드](../terraform/modules/network/subnets.tf)

보안 그룹은 리소스에 들어오고 나가는 트래픽을 제어한다. `alb`, `app`, `db` 그룹 세 개로 나눠 인터넷에서 ALB의 80·443 포트에 접근할 수 있게 했다. 앱의 8080 포트는 ALB 보안 그룹에서만, DB의 3306 포트는 앱 보안 그룹에서만 들어올 수 있게 했다. 출처를 보안 그룹으로 지정해 허용 대상의 IP가 바뀔 때마다 규칙을 고칠 필요가 없어졌다. [보안 그룹 Terraform 코드](../terraform/modules/network/security_groups.tf)

서브넷과 라우팅만 구성한 실습에서는 리소스 11개를 만들었다. 보안 그룹과 규칙을 추가한 네트워크 실습에서는 리소스 21개를 만들고, AWS CLI로 실제 규칙을 확인한 후 `terraform destroy`로 정리했다. 이후 배포에서도 Terraform 계획을 검토하고 AWS에서 생성 결과와 삭제 완료를 각각 확인하는 순서를 사용했다. [서브넷 실습 기록](devlog.md#서브넷인터넷-게이트웨이-구현-시드니), [보안 그룹 실습 기록](devlog.md#2026-11-10)

## 남은 과제

- **DB 부하 중 연결 풀 타임아웃.** ECS에서 DB 조회 요청을 동시에 보냈을 때 Hikari 연결 10개가 모두 사용됐고, 대기 요청이 30초 뒤 타임아웃됐다. RDS 자체 복구 이벤트도 비슷한 시간에 발생했다. 다음에는 일정한 요청량으로 시작해 Hikari의 사용 중·대기 연결 수, 쿼리 지연, RDS 지표와 이벤트를 같은 시간축에 놓고 어느 변화가 먼저였는지 확인한다. [DB 부하 실측](08-ha-observability.md#실습-결과-2026-11-19)
- **장시간 요청을 보내는 `ab`가 멈추는 조건.** 12분 실행 중 분당 요청이 약 3,921건에서 7건으로 줄었다. 짧은 실행에서는 연결 재사용 설정을 바꿔도 정상이라 30초씩 나눠 실습을 마쳤다. 다음에는 경로·동시 연결 수·연결 재사용 설정을 고정하고 실행 시간만 바꾸면서 맥의 도구 출력과 ALB 요청 수를 비교한다. [부하 재검증 기록](08-ha-observability.md#실측-결과-2026-11-24)
